# 网页分流可观测性与保守恢复（2026-10-27）

本地候选标识：`relay-reliability-dev-20261027`。不是已经发布的镜像标签；本轮不连接公司环境、不推送镜像、不更新 OCP。已有批注工具和锁屏修复一并保留，实际发布需对整个最终工作树做 CI。

## 行为

- 将接收画面和画面来源分开：新鲜的有效画面来自服务器直连时，显示“画面接收正常 · 服务器直连”，不再把可观看的服务器回退统称“故障”。没有新鲜有效画面/上报过期仍明确显示待确认或异常，不能冒称观看正常。接收验证不等于独立确认像素已显示在屏幕上。
- 分流失败区分连接超时、通道打开却无可验证画面、曾正常供画面后中断；保留原有 ICE、协商、密钥、协议和限流错误。不能仅凭这些结果判定公司防火墙或跨楼路由原因。
- 流量默认显示本次共享，另可选本次页面连接累计。同一共享轮次换源/成员变化不清零；房间或共享轮次变化才重新建立本次基线。各人数据仍是自身页面连接范围，断线新建对象会重置；不是全会议持久化账单。旧报告没有本次字段时显示 —，不借用历史累计冒充本次共享。
- 诊断只输出白名单字段：候选版本、时间、来源角色、历史错误代码、本次/累计计数、连接/ICE/通道状态、可用时的往返延迟、发送缓冲量，以及无身份的会议角色人数。绝不序列化整份 overview、用户姓名/账号、房间 ID、SDP、候选 IP、页面 URL、Cookie/令牌或任意原因文本。复制受限时可手动复制脱敏文本。
- 新接收者选源优先近期实际上报有效画面且前台的现有根节点，未知/失效上报不获质量加分。保留已有根和健康边，不因评分变化重排已有观众。后台不直接等同于不健康，不按大楼/网段猜位置，不扫描网络。

## 先保住服务器，再验证新同伴

原有立即故障换源仍有限尝试，失败回退仍受全服务带宽额度约束。

服务器直连的观众上报近期有效画面，距离失败至少 30 秒后，才可验证另一位已有根节点：必须有空位、近期上报有效画面，且该观众本轮没有在此节点失败过。每共享轮次最多追加两次，三个失败父节点总上限不变。创建失败、密钥失败、协议异常、超出接收上限不做追加自动重试。没有合适节点时继续服务器直连，不重新冲击原先失败的路径，不声称跨楼已经修好。

验证时 `role=peer, serverBackup=true`，服务器仍保留该观众原有直连带宽预约和实际供流。客户端验证两路数据、以同一播放序列门去重，不清空健康画布。两个至少相隔 2 秒的新鲜报告必须表明同伴有效帧继续增加（首次至少 3 帧，最近帧年龄小于 2 秒），服务器才撤掉直连并保留已建立的同伴边。这个证据仍是已认证浏览器自报，不是独立网络测量。

验证失败继续直连，即使此时恰好出现第三个空闲节点，也不能走旧的立即换源逻辑先撤服务器；下一次验证仍须经过冷却。验证者的父节点离开也恢复直连。探测不超出原先服务预算，根节点最大扇出 3 保持不变。正常的冻结转发者故障仍可能有检测/换源等待，不承诺所有故障场景零停顿。

## 自动验收入口

- `go test ./...`、`go vet ./...`：包括 `internal/meeting/browser_recovery_test.go` 的冷却、保留服务器、持续验证、失败/父节点离开、第三个空闲根节点出现时仍保留服务器、上限、旧代际、非法计数和保持健康边用例。
- `cd web; npm test; npm run build`：状态区分、本轮统计、密钥验证、后台恢复、脱敏白名单和回退验证期间继续接收服务器画面。
- `npm run test:relay`：原有真实本机 WSS/RTC 回归、锁屏模拟、三项新增恢复/诊断/桌面及窄屏测试。
- `npm run test:e2e`：完整普通页面/批注/权限/共享回归。
- `RELAY_CAPACITY_VIEWERS=32,64`、`RELAY_CAPACITY_SECONDS=30`、`RELAY_CAPACITY_FALLBACKS=6` 后运行 `npm run test:relay:capacity`：本机隔离会话合成画面测试，追加 6 名观众的实际服务器回退；保留帧率、CPU、堆和服务计数报告。回退故障由显式关闭 RTC 并阻止该观众重新创建 RTC 注入，不伪装成公司网络故障。

具体最终结果以本文件末尾验收记录及 artifacts 日志为准。32/64 会话不是 32/64 台真实电脑；连接/帧前进通过不等于高运动画面流畅认证，更不是公司跨楼、SSO 或物理锁屏验收。

## 发布与部署（不能跳过镜像发布闸门）

1. 在 `feature/browser-peer-relay` 核实包含全部预期变更的最终提交；不修改领导 main/正式标签，不混入本机日志、公司环境或凭据。
2. 按 `COMPANY_OCP_RELEASE_RUNBOOK.md` 手动触发最终提交的现有 `container.yml`；质量与镜像两个 job 都成功才继续。不要降低原有扫描/测试门槛。
3. 仅取同一成功运行的 `tested-container` 镜像；校验提交、归档 SHA-256、image config ID、labels、平台和非 root UID；建立唯一 prerelease、非 latest，保留核验记录。本地开发版本字符串不等于发布镜像存在。
4. 公司 Linux 普通 Podman 用户下载并核验本版归档，再 load、按确切 config ID tag、push 本版 JFrog 唯一标签；沿用已批准的 `--tls-verify=false` 仅用于该公司搬运步骤。登录令牌私下输入；绝不写入文档。记录实际 push 的 manifest digest，不把 config ID 当 digest。
5. 公司 Windows/PowerShell 更新前只读确认身份、目标 namespace/deployment/container、当前 rollout 健康、单副本 Recreate、现有 `/data` PVC、网页分流开关及显式人数上限。历史目标 `webzoom-uat` / `webzoom` 仍需现场复核，不能据此假定现场状态。
6. 预约无会议窗口；保存现场实际旧镜像引用到本版本专用且不存在的备份文件，再只用 `oc set image` 更新已核验镜像（优先 manifest digest 引用），等待 rollout。不要 apply 旧 YAML，不改 SSO/admin/Secret/CA/PVC/Route/env/安全上下文/已有带宽设置或人数上限。
7. 所有参与者刷新网页并核对新版本，避免旧页面脚本与新服务器混用；用三个账号做小范围“正常同伴、服务器回退、换共享者、锁屏恢复、批注授权”验收。公司跨楼是否可直连须现场观察，不能拿本机测试作保证。
8. rollout/验证失败时停止，读取诊断，使用刚保存的确切旧镜像 `oc set image` 回退并等 rollout；不猜旧标签，不覆盖备份。旧镜像备份不是 PVC 数据备份。

本地自动验收完成后，镜像尚未通过最终提交的 Linux CI/发布，就不能给出一个声称已存在的新镜像地址或让用户拉旧版充当新版。完整可直接粘贴的公司命令应在确定新 Release、SHA-256、config ID 和实际 registry digest 后按原交付流程生成。

### 32/64 会话及 6 人实际回退

同一台 Windows x64、16 逻辑 CPU、约 16 GB 内存电脑上的独立浏览器会话；共享源为 1280×720、请求 30 fps 的合成画布，不是高运动桌面/64 台电脑。

| 观众数 | 连通/帧前进/回退 | 故障后实际分配（另有 1 位共享者） | 稳定采样时长 | 最慢观众的区间平均解码速率 |
| --- | --- | --- | --- | --- |
| 32 | passed | 8 根节点 + 18 同伴 + 6 直连 | 30.50 秒 | 5.71 fps |
| 64 | passed | 16 根节点 + 42 同伴 + 6 直连 | 31.06 秒 | 2.74 fps |

两组注入故障后的所有观众均继续有帧前进、各保留一条控制 WSS，6 个目标观众均实际收到服务器数据。稳定采样阶段服务丢帧/拥塞计数增量为 0，但启动和故障阶段仍有丢帧，不能宣称全程无丢帧。Chromium 总 CPU 时间约 7–8 核，非服务器 CPU；堆变小不代表已经证明无内存泄漏。

**结论：连通、分配和回退验收通过，不通过“32/64 人高帧率流畅容量认证”这一更强的判定。** 最慢观众均低于 10 fps。单机资源竞争是测试限制，但不能据此反推真实公司电脑一定流畅；没有扩大到 100 人，也没有修改既有 64 观众硬上限/公司实际人数配置。
