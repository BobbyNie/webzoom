# 纯网页协作分流：第一版实现与验收记录

日期：2026-10-16。**已实现本机试验，不是公司已部署版本。**

## 先看结论

这版不用 Chrome 插件、不用 EXE，也不让同事填写 UDP 端口。所有人照常打开网页、登录、加入会议。中心只把画面给一位观众，该观众的网页把同一份压缩画面转给其他观众。

它的目的不是在所有指标上打败 UDP 广播，而是在保留网页体验的前提下，减少中心重复发送画面。

- 发布候选版本：`browser-relay-uat-20261016-r1`。此源码记录本地验收；是否已发布以对应 GitHub prerelease 的 CI/镜像证据为准。公司 OCP 未由本机修改。

## 1. 第一版实际做到了什么

```text
共享者 ──WSS──> 中心 ──WSS──> 观众 A（自动选定的网页转发者）
                                    ├──WebRTC DataChannel──> 观众 B
                                    └──WebRTC DataChannel──> 观众 C
```

所有人仍与中心保持登录、会议控制、批注和时钟连接。被分流的是画面，不是取消中心身份验证。

1. 服务端试验开关默认关闭；开启后，主持人仍需在会议未共享时手动开启本场试验。
2. **最多四人：一位共享者 + 三位观众；一个转发层，最多两个同伴接收者。** 第五人不予加入。
3. 自动选择转发者，成员进出或共享权转交时重新安排。转发者退出后，剩余可用观众接替中心供流。
4. 原始 VP8 压缩帧直接转发，不重新录屏、转码，也不获取摄像头或麦克风。
5. 页面显示角色、中心接收字节、已校验的同伴接收字节、向同伴发送字节。字节数按当前页面连接累计，不是假定的“公司节流百分比”。
6. 同伴连接失败时，向中心申请回退。额度充足才直连；额度不足会明确显示等待/暂停，不让全部观众无条件回源。
7. 保留原有小窗、批注、共享权转交与普通会议模式。关闭服务端开关时不会创建 WebRTC 连接。

**没有实现：** 多层树、跨办公室自动分组、跨 VLAN 自动选路、200 人扩容、原生 UDP 广播、边缘服务器、公网 STUN/TURN、后台常驻中继或任何插件/EXE。不能把本机四个浏览器会话说成四台真实办公电脑的结果。

## 2. 和 UDP 广播相比，效率怎么判断

必须区分“中心链路”“转发者上传”“质量与时延”“部署成本”。

| 指标 | 本次网页协作转发 | 真正的 UDP 广播 |
| --- | --- | --- |
| 中心重复发送份数 | 本试验正常状态只给一个转发者供流 | 若也只给一个中继供流，中心节省可相近；网页方案并非天然更省中心带宽 |
| 转发者本机发出份数 | 每位下游观众各发一份；两个下游就是两份 | 从广播发送者角度通常只发一份；交换设备在各出口怎样复制另算 |
| 电脑开销 | 浏览器验证、连接维护、加密和逐同伴上传；本次未测 CPU 上限 | 取决于原生程序的实现；不能凭协议名断言实际性能 |
| 丢包与时延 | 此版采用可靠有序 DataChannel；重传、排队可能延迟，因此过期帧丢弃并请求关键帧 | 裸 UDP 不自带重传或拥塞控制，需要程序另补；不能把不重传等同于画面更可靠 |
| 安装使用 | 不安装插件/EXE，不手填端口；仍须浏览器与 IT 策略允许互联 | 现有历史路线依赖原生组件及终端网络配置 |
| 公司是否可用 | 尚待三台真实电脑、批准网络路径实测 | 同样受广播域、终端防火墙与网络策略制约 |

**计算示例，不是测得的性能承诺：** 假设实际画面码率为 6 Mbps，三位观众：

- 原普通模式：中心发出约 `3 × 6 = 18 Mbps`。
- 网页分流：中心发出约 `6 Mbps`，观众 A 再向 B/C 发出共约 `12 Mbps`。
- 中心媒体出站理论下降约 **67%**；若把共享者上传也计入中心总媒体流量，则是约 `24 → 12 Mbps`，下降约 **50%**。
- 两位观众时，中心媒体出站理论下降约 **50%**，含上传的中心总量理论下降约 **33%**。
- 不包含帧签名、WSS/DTLS/SCTP/TLS、信令、重传等开销。码率、质量必须相同才可比较。
- 如果观众互传仍经过受限公司链路，中心发送份数下降也不等于该公司链路真正节流。不能仅凭私网地址、host ICE candidate 或“连接成功”认定在同一局域网。

因此推荐：**先验证网页方案能否在公司允许的网络下分流。它更贴合免安装需求，不宣称极限发送效率高于 UDP 广播。**

## 3. 传输与安全边界

- WebRTC 只用 DataChannel，`iceServers: []`，没有公网 tracker、STUN 或 TURN。信令只经过原有已认证 WSS。
- 服务端限定房间、拓扑代次、链路 ID、发送方向和单次 offer/answer；不向未分配的同伴转发信令。
- 信令只接受数据通道媒体段和私网/回环/链路本地 IP 或 `.local` 主机候选；不接受公网 IP、relay/srflx 候选或音视频媒体段。严格筛选可能使某些网络无法连接，这是保守限制而非绕过理由。
- 受信任的中心为每帧做 P-256/SHA-256 签名，绑定房间 ID、拓扑代次及原始 WZ01 帧（其中包含 epoch/序号/时间戳）。网页先验证，再显示或继续转发。
- 签名外封装为 104 字节；DataChannel 分块不超过 16 KiB，考虑协商后的最大消息大小。重组只有一个有界在途缓冲，最大约 1 MiB，超时 1 秒。
- 验证队列最多三个等待帧；通道发送缓冲超限停止发增量帧并请求关键帧，避免无限积压。超过 1 秒的画面不继续消费。
- 每个下游初始建立允许约 12 秒；此后约 4 秒没有有效媒体会申请受限回退。不存在“无限无条件重试回源”。
- 中心控制消息超过约 9 秒未续约，关闭同伴链路并重连验证登录。退出、会议结束、共享权转交会关闭或重建对应链路。
- **签名是来源验证，不是群组端到端加密。** DataChannel 使用浏览器的链路加密；本版没有应用层群密钥轮换。无法阻止已授权观众录制或私自转发已看到的内容。
- 候选路径信息只显示候选类型和协议，不输出电脑私网地址；UI 始终提示公司路径待现场核验。
- 浏览器可能受本地网络权限或企业策略限制；不要求同事关闭安全软件、允许全部 UDP、修改代理或申请摄像头权限来绕过限制。

## 4. 带宽保护的精确含义

试验服务启用时，按 **每条中心媒体流 8 Mbps** 做保守预约，包含共享者上传和每个获准中心接收者。考虑该服务所有活动会议；晚加入的转发者、普通模式新观众和失败回退都不能绕过预约检查。

还有一个服务级应用层发送预算：按“已经收到的原始媒体 + 本次将排队的媒体副本”计费，允许最多约一秒额度的突发。预算不足会丢弃排队媒体、请求关键帧并反馈拥塞。

**这不是网卡整形或物理硬上限：** 已经收到的上传无法追回，TLS/网络开销不包括在内；慢连接队列与实际发送时间也不同。现有管理员流量统计继续按实际媒体收发记账。不得将此机制宣传为公司链路的精确限速器。

等待额度的观众不会持续自动挤占中心。试验中如管理员调整额度或网络恢复，主持人可停止并重新开始共享，让服务重新安排；更精细的自动重试/公平调度仍属后续工作。

## 6. 下一次公司试验怎么验收

必须先按现有发布规程产出并核验本分支的独立测试镜像，再由授权人员更新测试环境。**现在没有可声称已经存在的镜像地址或 digest。** 保留公司现有 SSO、CA、PVC 和安全设置，不套旧部署 YAML，不改正式版。

试验版服务设置 `BROWSER_RELAY_ENABLED=true` 后：

1. 只找三台已获准互联的真实测试电脑、三个不同账号。你为共享者，两名同事为观众。三机已足够验证一个转发者+一个同伴接收者。
2. 主持人在还未共享时点“开启网页分流试验”，发同一个会议链接。各人只用网页，不装任何组件、不填写端口。
3. 开始共享持续变化的画面。某观众应显示“网页转发节点”，另一位显示“接收同伴画面”。
4. 同伴观众应实际看到更新画面，“已验证同伴收到”持续增加，“中心收到”保持 0（以新打开页面的这段连接为准）。转发者的中心接收与向同伴发送同时增加。
5. 关闭转发观众的页面，确认剩余观众重新得到画面；重新开会对比普通模式和分流模式，同内容、同码率、同人数。
6. 由 IT/网络侧核对中心出口和受限办公链路的流量、路由与终端间实际路径。页面的计数是重要证据，但不是该链路节流的充分证据。
7. 小窗、批注、共享权转交、退出登录、结束会议同时验收。性能建议记录连续 10 分钟的丢帧、恢复时间、p95 时延及转发电脑 CPU/上行。

若同伴互连被公司策略禁止，不能通过放宽全部终端防火墙来“做成功”；应回到提案中的“办公网边缘服务集中转发”备选。那仍可保留同事纯网页，但不属于本次已实现能力。

## 8. 公开资料与适用范围

以下原始资料于 2026-10-16 再次核对。用于选型，不是本项目的性能背书，也未复制第三方实现或增加其运行依赖。

1. Microsoft Learn, **Microsoft eCDN technical overview**：浏览器 WebRTC P2P 减少重复视频传输的工业方向；该产品 HLS/DASH/eCDN 能力不能直接等同于本项目的低延迟 VP8 帧试验。来源：`https://learn.microsoft.com/en-us/ecdn/technical-documentation/technical-overview`。
2. **RFC 8831 — WebRTC Data Channels**，2021-01，特别是 §4 的拥塞控制要求、§6 的 SCTP/DTLS 传输：支持通用数据对等传输；不保证任意公司网络都可达，也不保证低于广播的延迟。来源：`https://www.rfc-editor.org/rfc/rfc8831.txt`。
3. Halder et al., **fybrrStream: A WebRTC based Efficient and Scalable P2P Live Streaming Platform**，arXiv:2105.07558，2021-05-17：借鉴树/网状同伴分发研究方向，不把论文规模或指标当成当前四人试验的成绩。来源：`https://arxiv.org/abs/2105.07558`。
4. 此前调研的 Novage **P2P Media Loader** 面向 HLS/DASH 分片；因此本版没有把该库硬套进 WZ01/WebCodecs 流。详见旧调研的原始来源及限制说明。
