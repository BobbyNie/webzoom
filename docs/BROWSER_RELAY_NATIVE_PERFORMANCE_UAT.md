## 测试边界

- 单台 Windows 电脑，已安装的桌面 Chrome / Edge，隔离临时浏览器资料。
- 真正的 `getDisplayMedia` 采集专用动态 HTML 标签页，原生 VideoFrame、VP8 编解码、WSS 和 RTCDataChannel。无 Canvas 合成流替换、桌面/业务窗口、麦克风或系统音频采集。
- 页面中两块色条持续移动；背景 RGB 切换用于验证观众确实解码了新画面，不只检查角色或连接状态。高动态页面约每秒更新 165 次，但采集目标上限仍为 30 fps。
- 不代表跨物理电脑、不同楼层、公司网络、64/100 人或生产环境验收；同机 UDP 同伴单播不是广播或组播。

## 找到并修正的问题

### 1. 限帧计时丢帧

旧逻辑每收到一帧就重新计算下一帧的间隔，接近 30 fps 的输入带有很小的调度抖动时会误丢下一帧。先写失败用例：30 个带 ±1 ms 到达抖动的输入，仅编码 20 帧。改成保留目标节拍、长时间停顿后跳过过期时隙，现为 30/30。

同时覆盖 60 fps 输入限制为 30 fps、长停顿后不突发追帧、被跳过帧及时释放、编码异常释放两个帧句柄并停止采集。

### 2. 共享端不必要的 Canvas 往返

旧链路先把原生采集帧画到临时 Canvas，再画到预览，并从临时 Canvas 创建编码帧。现在直接从原生 VideoFrame 创建供编码器使用的帧，由编码器按配置缩放；本地预览单独绘制。保留编码队列、带宽背压、自动降级、关键帧及资源释放保护。

单元测试验证原生帧资源被传给编码器、仅一次预览绘制、较大输入仍按 1920 × 1080 上限配置输出。下列原生浏览器测试用于验证真实编解码行为，而不只依赖模拟测试。

### 3. 目标与实际帧率分开显示

画质卡原来只显示“1080p · 30 fps”等配置档位，容易被理解为实际效果。现在明确显示“目标”和“实际：宽 × 高 · fps”，无共享时不把旧数据当作当前结果。

## 原生处理链路诊断

独立 Chrome 共享端 + 三个独立 Chrome / Edge 观众。每阶段预热 3 秒、测量约 30 秒；同一动态 DOM 源，高动态与低动态分开计时。只对原生 reader.read、encoder.encode、WebSocket.send 加透明计数包装，转发原参数与结果；没有额外消费帧或替换媒体。持续共享压力测试不装这些计数包装。

| 版本 / 场景 | 采集 fps | 进入编码 fps | 发出 fps | 三位观众平均接收 fps 范围 |
|---|---:|---:|---:|---:|
| 优化前，高动态 | 29.93 | 4.89 | 4.89 | 4.83–4.83 |
| 仅限帧修正，高动态 | 30.00 | 4.03 | 3.93 | 3.96–3.96 |
| 限帧 + 原生帧直接编码，高动态 | 30.03 | 29.66 | 29.66 | 28.93–28.96 |
| 优化前，低动态 | 10.02 | 6.96 | 6.96 | 6.73–6.73 |
| 仅限帧修正，低动态 | 10.02 | 9.92 | 9.92 | 9.79–9.85 |
| 限帧 + 原生帧直接编码，低动态 | 9.98 | 9.98 | 9.98 | 10.08–10.18 |

最终轮高动态时共享端显示实际 `1198 × 1080 · 29 fps`，没有自动降级；低动态时实际约 10 fps。这不表示低动态场景被限制到 10 fps，而是该阶段源页面约 10 Hz 更新、采集也约 10 fps，没有人为补帧。采样边界与在途帧会令接收统计短时略高于采集。

这是顺序进行的本机诊断，不是随机化性能基准。仅限帧修正没有改善本轮高动态效果；高动态大幅提升出现在去掉 Canvas 往返后，不能把所有提升都归于限帧修正，也不能据此承诺任何设备上恒定 30 fps。

### 调试失败也留档

早期诊断曾出现源 DOM 仍更新、原生采集却停止增长的失败。测试页使用模拟 viewport，改用实际浏览器窗口尺寸 `viewport:null` 后，高低动态两阶段均持续增长。疑似低动态更新区域落在实际可采集窗口以外，尚未单独隔离确认，因此没有认定为已修好的产品问题。失败报告也保留，不用合成流替代通过。

## 六位观众持续共享与故障恢复

2026-10-21 本地时间 `15:24:07` 开始，全用例耗时 `437.180 秒`，`1/1` 通过。Chrome `155.0.8059.39`、Edge `155.0.4283.62`。

| 项目 | 实际结果 |
|---|---|
| 原生高动态连续共享 | `364.519 秒`，约 6 分 4 秒；与之前短测分别计时 |
| 浏览器 | 1 个共享端 + 6 个观众，独立进程，后续逐个补入故障节点的替代观众 |
| 拓扑 | 2 个服务器供流转发节点 + 4 个同伴观众 |
| 六位观众平均解码帧率 | `28.47 / 28.50 / 28.48 / 28.45 / 28.50 / 28.48 fps` |
| 源页面更新 | `158.63 Hz`，采集/发送目标仍为 30 fps，不生成重复帧 |
| 结束时共享端实际画质 | `1198 × 1080 · 30 fps`，未降到低档位 |
| 稳定期连接 | 各观众连接数未增加；四位同伴服务器媒体接收累计始终为 `0` |
| 实际网络 | 各观众连接均有原生 `host / udp` 候选及有流量的开放 DataChannel |
| 完整关闭转发浏览器 | 3 次，剩余观众均自动重排并收到新颜色；每次补入观众恢复六人 |
| 关闭到新像素确认 | `2965 / 3123 / 2734 ms`，包含自动化轮询，不是媒体延迟或精确断画时长 |
| 观众真实刷新 | 1 次，自动重新加入且确认新像素，含自动化等待 `2065 ms` |
| 停止 → 原生重新采集 | 连续 3 次，停止后角色关闭、连接清理，再次采集和像素确认均通过 |
| 页面未捕获错误 | `0` |

每约 10 秒检查所有观众帧数增长并切换 RGB 背景确认新像素。测试循环的等待及确认都计入连续期，因此总连续时间超过配置的 300 秒。系统可用内存采样为 `1623–2597 MiB`，这不是应用内存占用或泄漏检测。

稳定期末两位转发节点分别从服务器收到约 `101.99 MB` 画面数据，四位同伴分别从同伴收到约 `101.73–101.75 MB`（十进制），两位转发节点分别累计向同伴发送约 `305.77 MB / 101.93 MB`。这些是单机实际分流统计，不是公司出口节省量；也没有把同一电脑的六个浏览器说成六台电脑。

源页与同伴完整截图已保存并逐一查看；源页页眉的 `red · low` 是未随模式/背景更新的初始占位文字，不能用它判断实际模式。脚本在开始共享前设置 `motionMode='high'`，原生阶段采样与源更新计数记录于报告。持续测试没有 reader/encode/send 计数包装。
