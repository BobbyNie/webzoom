## 1. 结论与决策摘要

**有条件可实现。** 保留 OCP 上的认证、会议控制与媒体入口，为每场会议、每个经过实际可达性验证的局域网接收组，选择一台参会电脑作为中继。OCP 每组发送一份媒体，中继在自己的 IPv4 广播域内发送真正的 UDP 广播，其余成员本地接收。

这不是普通 WebRTC 单播，也不是让 OCP 向办公网广播。初版使用 **Chrome Manifest V3 扩展 + 普通用户权限运行的 Windows 辅助程序**。所有需要广播收发的参会电脑都需要这两个组件。

条件与边界：

1. 用户安装、升级、运行、卸载都不得要求管理员身份；不安装系统服务、驱动，不关闭安全控制。
2. IT 可以提前审批软件并下发扩展、程序执行和防火墙策略。**“免管理员安装”不能替代这些策略。**
3. 初版覆盖 Windows 桌面 Chrome、获准的 IPv4 有线网络。Edge、无线、VPN、IPv6-only、终端隔离网络不自动宣称支持。
4. 必须通过两机权限/广播试验、真实 VP8 端到端性能试验和多网段试验后，才进入完整产品开发。
5. 20 Mbps 为需求给出的链路上限；其计量点、方向及是否与其他系统共享仍待确认。不能保证任意网段数、任意画质、任意并发会议都能容纳。
6. 若 Native Messaging 媒体桥吞吐、公司策略或广播链路不达标，必须暂停并修订架构，不能宣布“方案已验证”。

## 2. 需求整理

| 编号 | 已确认的需求 | 说明 |
| --- | --- | --- |
| R01 | 降低 OCP 媒体发送带宽随观众人数增长的压力 | 不是仅减少 CPU 或增加副本 |
| R02 | 约 20 Mbps 的网络上限 | 单位为 bit/s，不是 MB/s；监控口径待核对 |
| R03 | 每个局域网分组选一个参会端转发 | 分组数和组内人数不写死；不是固定两组或每组五人 |
| R04 | 组内使用真正的 UDP 广播 | 不把多条单播连接冒充广播；组播是另行审批的替代方案 |
| R05 | 开发 Chrome 插件 | 此处具体化为 MV3 扩展，并配套用户级辅助程序 |
| R06 | 普通用户安装和运行 | IT 预置策略允许；安装器不得提权或修改系统防火墙 |
| R07 | 保留现有 SSO、会议、共享权转交功能 | OIDC 令牌继续只存在服务端 |
| R08 | 当前先交付方案并在独立分支评审 | 不修改正在运行的 OCP，不实现或发布客户端 |

以下是为使产品可用而提出、尚需确认的非功能要求：中继故障切换、丢包恢复、媒体机密性与来源验证、退出/失效后停止获取后续画面、总带宽准入、明确的失败提示和运维指标。

## 3. 当前系统与改造边界

已检查的核心链路：

- [媒体编码](../web/src/media.ts)：屏幕采集 → VP8 → `Publisher.output()` → WSS；只共享画面，不包含音频。
- [画质档位](../web/src/quality.ts)：目标码率依次为 6、4、3、1.8、1.2 Mbps；不是固定每人 1 Mbps。
- [Hub.Publish](../internal/meeting/hub.go)：把同一媒体帧送入每个非共享者的媒体队列。
- [WebSocket 服务](../internal/server/server.go)：每个 Peer 单独写二进制媒体；验证 Cookie、Origin 和当前会话。
- [媒体协议](../internal/media/frame.go)：`WZ01` 帧，32 字节头，整帧上限 1 MiB。
- [浏览器帧校验](../web/src/protocol.ts)：检测序列缺口；超过 1000 ms 的画面被视为过期。
- [现有接口](PROTOCOL.md)：同一身份在同一会议只允许一个连接；Cookie 续期不能重启媒体。
- [部署](../deploy/openshift/deployment.yaml)：单副本、Recreate；会议和会话仍在内存中。

保留 Go、React、WebCodecs VP8、SSO、HTTPS/WSS 与单实例约束。新增局域网传输层；不是切换编码格式、增加 HPA 或开放 OCP UDP 端口。初版不包含独立 WebRTC/TURN、音频、摄像头或跨网段广播路由。

## 4. 目标结构

```text
共享者浏览器 -- WSS 上传一份 VP8 --> OCP：校验共享权、会议 epoch、帧序列
                                         |
                           每个被准入的接收组一份 WSS 媒体
                    +--------------------+--------------------+
                    v                    v                    v
                A 组中继浏览器       B 组中继浏览器       C 组中继浏览器
                    |                    |                    |
                扩展 + 辅助程序      扩展 + 辅助程序      扩展 + 辅助程序
                    |                    |                    |
             本地 IPv4 UDP 广播  本地 IPv4 UDP 广播  本地 IPv4 UDP 广播
                    |                    |                    |
               A 组接收程序         B 组接收程序         C 组接收程序
                    |                    |                    |
               扩展 → 网页解码      扩展 → 网页解码      扩展 → 网页解码
```

所有浏览器都保持自己的已认证会议 WSS 控制连接。普通组员的连接不再接收二进制视频，但仍接收会议状态和授权事件。不能把“停止视频 fan-out”误做成“断开非中继成员”，否则会破坏权限和续期。

**辅助程序不另行加入会议，不读取/复制 HttpOnly Cookie，也不接触 OIDC access/ID/refresh token。** 媒体与控制经已有浏览器连接进入扩展，避免违反一用户一会议一连接的限制。

初版不选择当前共享者作为下行中继：共享者本地看预览，其独处的接收组无需服务器下行。共享者所在组若有其他观众，由其中一名观众担任中继。牺牲这一小项优化，可以统一来源校验和切换行为；以后再评审共享者直接本地播发。

## 5. 插件、辅助程序与普通用户安装

### 5.1 职责

- 网页：会议身份、共享采集、WebCodecs 解码、媒体路径选择和状态提示。
- MV3 扩展：仅接受批准的 WebZoom HTTPS origin、顶层会议页面的外部连接；建立 `runtime.connectNative()` 长连接；验证消息 schema、会话绑定和大小。
- 用户级辅助程序：网卡信息、UDP 探测、收发与重组、签名/加密校验、进程级资源限制。建议使用 Go，并为 Windows socket 的网卡选择/包信息补充平台层。
- OCP 服务：权威会议成员、组/中继租约、定向媒体分发、源签名、组密钥和带宽预算。

扩展 manifest 使用 `nativeMessaging` 与精确的 `externally_connectable.matches`。辅助程序 manifest 的 `allowed_origins` 只允许指定扩展 ID。不使用 `<all_urls>`、任意进程执行或任意目标地址的通用代理接口。网页 origin、会议实例、页面连接必须共同绑定；页面导航、端口断开或注销时清理授权。

### 5.2 用户安装

建议目录 `%LOCALAPPDATA%\WebZoom\Relay\`；程序清单声明 `asInvoker`；Native Messaging host 注册到 `HKCU\Software\Google\Chrome\NativeMessagingHosts\<host-name>`。不写 HKLM、Program Files、系统证书存储，不创建服务或系统计划任务。

扩展正式分发选其一：经批准的 Chrome Web Store 分发；或公司托管 Chrome 的企业策略自托管分发。**Windows 上自托管扩展不能依靠普通用户双击 CRX 正式安装。** 开发者模式仅限经批准的试验设备，不作为上线方案。

辅助程序须签名、版本化、支持用户级卸载/回滚；不把“有签名”当成已获企业放行。升级后路径变化与防火墙/应用控制规则须一起验证。固定扩展 ID、稳定安装目录、签名更新包和升级期间会议提示属于发布要求。

### 5.3 防火墙与接口

IT 提前批准指定程序和限定 UDP 端口、网络 profile、源地址范围。安装器只检测策略，不自行增加规则或让用户关闭防火墙。

实际端口由公司批准后配置，本文不指定看似已经开放的端口。优先一个 UDP 端口复用多会议，以认证后的 room/group 字段区分。

使用 IPv4 UDP datagram socket 和 `SO_BROADCAST`，不是 raw socket。多网卡场景必须按选定接口发送到其本地子网广播地址，且检查接收接口/目的地址；禁止向所有网卡、所有地址或跨网段扫描。Windows 可用 `WSARecvMsg`/`IP_PKTINFO` 获取包信息，具体 Go 封装需在 G0 实测。不得复制 Linux-only 的绑定方式假称 Windows 可用。

一个浏览器 profile 内共享一个 native host，复用会议。初版一台电脑同一时刻仅支持一个广播接收 host；第二个 profile/Windows 会话遇到占用要明确报错。不得用无约束 `SO_REUSEADDR` 掩盖冲突；独占端口、共享机器冲突和释放行为列入验收。

## 6. 网页到本地程序：明确选择一条可验证的数据通道

初版采用 **Native Messaging JSON 分块桥**，不启动 localhost HTTP/WebSocket 服务，不安装本地 TLS 根证书，也不关闭浏览器的本地网络访问安全机制。

原因：普通扩展没有可直接替代用户级 UDP 程序的通用 socket 能力；旧 Chrome Apps 的 UDP API 不是本方案可依赖的 MV3 API。IWA 的 Direct Sockets 是另一种应用分发模型，不能当作普通扩展权限。

官方 Native Messaging host→Chrome 单条消息上限为 1 MB，且使用 JSON；原项目整帧最大 1 MiB，base64 后更大，所以**绝不能把整帧直接放进一条消息**。

拟定桥协议：

- 原始块最大 48 KiB，base64 为 64 KiB，再加受限元数据；整条序列化 JSON 最大 96 KiB。双向都采用相同限制。
- 一帧拆为约 22 个块（对 1 MiB 原始帧而言）；签名外壳也计入上限。接收方验证 frameId、块索引、总长和总块数后重组。
- 浏览器↔扩展的 Chrome 消息传递同样使用 JSON；不假设 ArrayBuffer 会零拷贝传输。
- 使用明确的接收 credit/ACK、每会议有界队列和丢弃策略。控制/撤权/心跳优先于媒体，不能被大量数据块饿死。
- native stdin/stdout 只用于协议；长度前缀为官方协议要求的 32-bit native byte order；日志写 stderr，且不含媒体或密钥。
- 中继路径：浏览器收到 WSS 二进制 → 扩展分块 → helper 重组 → UDP 分包；接收路径反向执行，恢复原始 `WZ01` 后交给现有 Receiver。

**这是 API 可行但吞吐尚未证明的方案。** 每 6 Mbps 原始媒体，仅一次 base64 化即约 8 Mbps 本地文本量，另有多次 JSON、复制、IPC 和解码开销；这些不是 OCP 额外网络流量，但会消耗终端 CPU/内存。必须验证后台标签页、多会议和关键帧突发。未通过 G1，不承诺 1080p/30fps。

如果不达标，应单独提交替代 ADR（例如受管 IWA 或经批准的本地二进制通道）；不得偷偷切换不安全 ws://、带自签证书的 wss://，或恢复每人 OCP 拉流。

## 7. 分组、中继和状态机

### 7.1 分组不等于 IP 文本相同

网卡 IPv4、prefix、管理员配置的站点标签只是候选信息；相同前三段、相同出口 IP、相同 subnet 字符串均不能证明同一个广播域。不同站点可能使用重叠私网地址；无线客户端隔离也可能导致同子网不互通。

按会议授权进行低频探测：

1. 已登录页面上报受限的可用接口信息；helper 可只选择公司批准的接口。
2. 服务器给候选发送者一个短期随机 challenge，给待验证接收者 probe ID，但不提前给出 challenge 内容。
3. helper 在被准许的接口广播带 probe ID 的 challenge。收到的成员通过自己的认证 WSS 回报内容。
4. 服务器验证时间窗口、发送者、成员资格和 challenge，形成“该候选 → 这些接收者”的实际可达关系。
5. 验证结果不是安全身份凭证，也不具备传递性；改变中继或网卡后必须重新确认覆盖。禁止因此认为所有接收者互相都可达。

这类探测只证明当时能收到小包，不能证明持续视频容量。大流量准入仍需健康指标与实际试验。广播控制包不含用户名、邮件、SSO token 或完整会议邀请。

### 7.2 选举和租约

由单实例 OCP 服务统一授权，不让浏览器自行争抢主节点。优先接口稳定、广播测试通过且有资源的观众；第二个加入的人可能被选中，但不构成固定规则。

建议状态：`control-only → probing → receiver / relay-active → recovering → receiver / relay-active / unavailable`。一个人可在不同会议承担不同角色；初版默认最多同时中继一场会议，修改上限必须重新测量。

拟定心跳 2 秒、失联 6 秒、租约 8 秒，均为待测试起点。服务端签发单调递增 `relayGeneration` 和有期限的租约。helper 用本地单调计时器及会话期限共同限时，时间偏差过大拒绝激活。

切换：停止旧供流 → 撤销旧 generation → 轮换组密钥 → 验证新中继覆盖 → 发新租约 → 请求关键帧 → 恢复播放。新接收端只接受当前 generation。正常客户端在控制连接丢失、租约过期或 native port 关闭时停止播发/显示。

“服务端只授权一个”不意味着物理网络绝无旧 UDP 包：切换与网络分区可能有短暂残包。generation/key fencing 阻止其成为有效新画面。若未来采用双发平滑切换，额外流量必须预留，初版不默认双发。

## 8. UDP 媒体协议与恢复

保持 `WZ01` 内层媒体格式不变，新增独立版本的 LAN 外层；不能把未来协议宣称为当前 `PROTOCOL.md` 已支持。

外层必须能表达：协议版本、随机会议实例 ID、随机分组 ID、媒体 epoch、relay generation、密钥 ID、原始帧序列、分片索引/总数、总长、datagram counter、加密认证信息。详细字节布局、规范化签名编码和固定测试向量在 G2 前冻结。

- 初始 UDP payload（包括应用头、密文及认证标签）上限 1200 字节；这是保守起点，不是对所有路径 MTU 的保证。不得发送 1 MiB UDP 包或依靠 IP 分片。
- 先验证头部长度、房间/分组/generation、AEAD 和资源配额，再分配重组内存。绑定接收网卡，丢弃未授权接口数据。
- 原始媒体最大 1 MiB；签名外壳另有固定小额上限（设计上限 2 KiB）；单帧分片数最大 2048。拟要求每个1200字节UDP payload中的应用头、nonce和认证等开销合计不超过320字节，保留至少880字节数据，最大封装帧约需1194片，低于该上限；冻结协议时须重新计算，不能让任意长头字段破坏预算。
- 每会议重组内存初始上限 8 MiB、最多 8 帧；整个 helper 初始总上限 32 MiB（仅重组预算，不是总进程内存承诺）。设置按源/组包速率限制。
- 初始重组超时 250 ms，必须在现有 1000 ms 过期窗口内完成 IPC、网络和解码；超时、缺片或序列缺口后丢弃相关依赖帧并等待关键帧。
- 关键帧请求经已认证控制通道聚合、限流，沿用当前每房间至少 500 ms 的请求间隔；不让每个 UDP 丢包触发全网反馈风暴。
- 对关键帧突发做 pacing，不逐包立即轰炸网卡。使用测量后的广播速率上限与健康反馈；UDP 自身没有拥塞控制。
- 初版不承诺可靠重传或 FEC。若现场丢包使关键帧恢复无法满足质量门槛，必须增加经预算的修复机制或判定该网络不支持，不能靠无限关键帧请求掩盖。

丢包风险不能低估：若一帧含25个UDP包、各包独立丢失概率1%，整帧至少缺一包的概率约22.2%；大关键帧分片更多，完整到达概率更低。这是数学示例而非实测。仅靠关键帧重试的初版适合先验证低丢包有线网络；没有通过质量门槛之前，不承诺可用于存在明显丢包的网络。

广播覆盖同一广播域，包括未参会设备，且 Wi-Fi 的广播行为可能与单播显著不同。人数不直接放大中继“发送的份数”，不代表交换机、无线空口或每台终端没有成本。

## 9. 安全、授权、来源和撤销

### 9.1 两种不同保证

**媒体保密**与**媒体确实来自被授权的共享者**不是一回事。仅使用所有组员共知的 AES 密钥，不能阻止恶意组员伪造媒体。

拟定做法：

1. OCP 先按现有规则验证发布者、媒体 epoch 和 sequence。
2. 对每帧及其固定上下文（协议域分隔符、服务器/会议实例、epoch、sequence、长度和媒体字节）计算签名。候选算法是标准库 ECDSA P-256/SHA-256；确定性编码与签名格式在实现前冻结，使用跨端测试向量。算法/模块是否符合公司密码合规要求另行审批。
3. 公钥和其 key ID 通过已认证 HTTPS/WSS 会话传给获准页面，再经绑定的扩展通道交给 helper；不得信任 UDP 包自带的公钥。信任起点仍是现有浏览器 TLS/SSO，不是新的匿名 UDP 身份。
4. 服务器为每个组和发送 generation 分配独立的随机 AES-256-GCM 密钥，经各成员自己的已认证控制连接下发。辅助程序在内存中保存，不写日志或注册表。
5. 中继对分片做 AEAD；头部上下文作为 AAD。完整重组后验证 OCP 帧签名，成功才把原始 `WZ01` 交给网页。

这不是声称已通过密码审计。禁止自创加密原语；应用封包、nonce、签名编码、轮换和密钥生命周期必须进行独立安全评审。

### 9.2 nonce、重放与轮换

- 每个发送 generation 使用新密钥；同一 key 下 96-bit nonce 由不回退的计数器生成。helper 重启或计数器丢失后不得复用旧 key，从服务端申请新 generation/key。达到限额前轮换。
- 正常广播只由授权 relay 产生。按 key/generation 检查重放窗口，同时检查帧 sequence 和现有媒体过期时间。
- 重新选举、撤权、成员离开、会话失效和会议结束均触发相应的停流/密钥轮换。为阻止新成员解密旧录包，成员加入也轮换；入会批次可以短时合并，但撤权不得被无限推迟。
- 轮换由服务端序列化，通知新 generation/key 与生效边界。未确认准备好的成员暂时无画面，不无限保留旧 key 或回退旧 epoch。
- key 下发等控制流量随成员数增长，必须纳入预算，不能声称整个系统带宽完全与人数无关。

### 9.3 不能承诺的安全属性

现有项目是“已登录且持有链接者可加入”，不是新增审批制保密会议。这个访问模型应保持显式，不凭空宣称已具备邀请名单授权。

服务端发现退出/会话失效后，靠更换后续媒体密钥阻止旧密钥继续解密；仅让网页清屏不足以抵抗自制接收程序。已经下载或录屏的旧内容无法撤回，获授权参与者仍可转录/转发；被攻陷的终端、被攻陷的获准网页和恶意参会人的 DoS 不在本方案完全防御范围内。

SSO 撤销感知沿用当前应用的刷新/过期边界，并非新增 Keycloak 即时 backchannel logout。必须区分“应用获知撤权后停止供流”和“身份服务发生撤权后立即获知”。

## 10. 容量模型、准入和降级

令 `Rj` 为第 j 场会议实际目标码率、`Gj` 为需要服务器供流的组数、`Dj` 为经批准的直连回退数：

```text
稳态媒体出口 ≈ Σ[Rj × (Gj + Dj)]
实际链路流量 = 媒体 + WSS/TLS/TCP 等开销 + 控制/密钥 + 突发/切换 + 其他共享业务
```

若 20 Mbps 同时计算发送和接收，还需加入各共享者上传流量，不能只计算出口。

| 每场接收组数 | 每路 1 Mbps（假设） | 每路 6 Mbps（当前最高目标） |
| --- | ---: | ---: |
| 2 | 2 Mbps | 12 Mbps |
| 10 | 10 Mbps | 60 Mbps |
| 20 | 20 Mbps | 120 Mbps |

仅做稳态算术，不含开销，不是容量保证。1 Mbps 不在当前预置档位中，若选它须新增画质配置并验收文字清晰度。

预算应由服务端统一控制：

- 初始讨论值：若限制仅为独占出口，可先把媒体预算设为不超过 16 Mbps，给控制等预留至少 4 Mbps；最终值以计量点、其他业务和实测开销为准。
- 新组、直连回退、切换双发、多场会议都先申请预算。预算不足，先拒绝额外媒体订阅，显示原因；不得被动等到链路拥塞。
- 整体 token-bucket/pacing、单场峰值限制和观测是互补措施。不能仅依赖编码器平均目标，因为关键帧和网络重传会产生突发。
- 调度放在异步媒体分发层，不能在 `Hub.Publish` 的全局锁内 sleep、签名或等待网络。完整帧要么进入有界调度，要么丢弃并恢复关键帧，不能半帧截断后当正常媒体送出。
- 现有写超时 1 秒、8 帧/2 MiB 队列、1000 ms 过期阈值和新 pacing 必须联合验证；不以无限增大队列“解决”瓶颈。
- 应用统计只涵盖其负责的数据。若要求对物理 20 Mbps 做硬上限，需网络/平台在对应计量点落实 shaping/QoS；本应用不能限制其他进程或 TCP 重传产生的全部线速流量。

初版保留会议级统一画质，不承诺每组不同质量：目前只有一条编码流。一个网络较差的组不得无限拖累全部组；可以暂停该组并提示，具体策略由验收决定。分组独立画质需要多路编码/分层编码，是后续项目。

## 11. 失败处理、兼容和运维

| 场景 | 预期行为 |
| --- | --- |
| 未装扩展/helper、版本不兼容 | 明确显示安装/升级提示，默认不自动 OCP 全量直连 |
| 广播被拦或有终端隔离 | 探测失败，不伪装为可用；人工批准且预算充足才直连 |
| 中继断网、休眠、退出 | 撤销租约、换 key、重新验证和选举；短时冻结后恢复或明确失败 |
| 共享者切换/停止 | 沿用权威媒体 epoch，清掉旧重组、队列和播放状态；必要时重选中继 |
| 网卡/VPN/网络 profile 改变 | 撤销旧路径，重新探测；不把流量泄漏到新出现的网卡 |
| 控制连接断开、续期失败 | helper fail closed；服务端按授权变化停流/换 key |
| OCP 重启 | 会议和会话仍需重建；旧服务器实例/租约全部失效，不宣称高可用 |
| 多 profile/其他程序占用端口 | 清晰报错，不抢占端口、不提权 |
| CPU/内存/组数/预算不足 | 拒绝或降级到经确认的画质；所有降级必须可见并计入指标 |

新增开关默认关闭；只有完成验收的用户/会议逐步启用。配置名称在实现阶段确定，本文不提供假装可用的环境变量。

监控至少包括：每会议组数/中继数/回退数、WSS媒体字节、链路计量点字节、UDP发送量、IPC队列/延迟、关键帧等待、丢片/恢复、租约切换、预算拒绝、实际画质。日志用短期节点标识；IP等网络元数据最小化且不进公开报告。

**回滚不是让全部组员突然恢复 OCP 单播。** 应先停止/暂停媒体，确认剩余直连人数和画质在预算内，再回滚功能或版本。保持单副本部署约束，不修改 SCC、特权或现有 SSO 策略。
