# 网页分流：容量采样与异常恢复（2026-10-21）

后续状态：同日已追加 Windows 全量后端检查、安全审计与延长实测；最新结果和仍缺的发布闸门见 [本地就绪检查](BROWSER_RELAY_LOCAL_READINESS_UAT.md)。下文保留本阶段当时的记录。

分支 `feature/browser-peer-relay`，仅本地未提交工作树；没有发布、推送或访问公司环境。本文区分工程回归、单机容量采样和现场验收，不把三者混为一谈。

## 本轮改动

- 新增独立的容量采样入口：16 / 32 / 64 位观众，逐级运行、单 worker、阶段失败即停。加入前检查本机可用内存，低于 512 MiB 时清理已创建会话并停止，不把机器内存不足当作产品人数上限。
- 新增持续共享入口：默认真实运行 10 分钟，可显式设置 1 分钟到 2 小时。容量与持续共享使用独立结果目录，避免相互覆盖。
- 两个入口固定使用 `https://127.0.0.1:19443` 和虚拟 OIDC，没有公司凭据、生产目标参数或公网 ICE 服务。自签名证书忽略仅用于本机测试。
- 每个会话使用真正的 Chromium、WebCodecs 解码和原生 WebRTC DataChannel；只替换屏幕选择器为 1280×720、请求 30 fps 的动态合成画面，不替换传输或解码。
- 新增四轮停止/重新共享检查：旧连接释放、停止后计数不再增加、新轮次恢复解码；以及真实 WSS 主动关闭后，在短暂离线期间阻止重连，恢复网络后自动重新入会。
- 新增两小时逻辑时钟测试：前端控制租约及连接复用、后端 64 位观众下 12 轮共享和旧轮次拒绝。这不是两小时真实视频播放。
- 修正接收端每一帧都会重新设置 canvas 宽高的问题：分辨率不变时复用画布存储，仅尺寸变化时调整；保留解码帧释放逻辑。新增稳定尺寸、尺寸变化、绘制异常释放的单测。不据此宣称特定百分比性能提升。
- 测试画面在采集轨道停止后不再继续绘制，避免测试夹具本身累积无用动画任务。

## 验收口径

容量测试的硬断言是：每位观众持续解码、拓扑符合一带三、只有正常转发节点从服务器接收、无意外重连、会话数正确。它不是流畅度认证。低于 10 fps 会写入报告提醒；10 fps 只是提醒阈值，不是已经商定的业务合格标准。

每次采样保存：

- 每位观众的角色、累计处理帧数、服务器/同伴字节数、连接数和拒绝计数；
- 服务器媒体计数器的差值、丢帧和拥堵上报；容量阶段另分开记录启动收敛期与稳定期；
- 本机 Chromium 已观测进程的 CPU 时间、各页面 JS 堆和主线程任务时间，以及本机硬件信息。退出进程的完整 CPU 时间无法补齐；这些不是服务器 CPU、整机 RSS 或无泄漏证明。

采样不注入网络丢包、延迟或带宽整形。离线恢复用例验证的是 WSS/重新登录校验/重新入会，不等同于拔网线、切换 Wi-Fi、WebRTC ICE 路径恢复或系统睡眠唤醒。

## 实测结果

- 前端 54 项单测、类型检查、生产构建通过。
- 网页分流 7 项真实浏览器回归通过（约 1.5 分钟）。
- `go test ./internal/meeting ./cmd/webzoom` 与 `go vet ./cmd/... ./internal/...` 通过；后端两小时逻辑时钟回归实际只运行约秒级。
- 普通会议/小窗/批注/SSO 62 项浏览器回归全部通过（约 2.3 分钟）。
- 最终容量重测 3/3 通过（约 2.9 分钟），无页面未捕获错误；每位观众持续解码，稳定期没有新增同伴连接。真实持续共享 1/1 通过，实测稳定期 600.10 秒（整项含建会与清理约 10.2 分钟）。

2026-10-21 本地约 12:05–12:08，Windows x64，16 个逻辑处理器、约 15.37 GiB 物理内存。每阶段另有一位共享者；各阶段顺序运行，没有同时运行其他浏览器测试。下表帧率是稳定采样期间“每位观众平均解码帧率”的最小值，不是逐帧最低值或延迟指标。

| --- | --- | --- | --- | --- | --- |
| 16 | 4 / 12 | 30.12 | 14.11 | 0.355 / 1.468 | 0 / 0 |
| 32 | 8 / 24 | 30.17 | 7.29 | 0.242 / 1.982 | 0 / 0 |

同伴接收者的服务器媒体接收字节均为零。启动收敛期并非零丢帧：16 / 32 / 64 人阶段分别记录服务器丢帧 3 / 0 / 29，拥堵上报 1 / 1 / 2；上表只统计启动完成后的稳定期，不能用它掩盖启动现象。服务器丢帧为零也不表示每帧都在各浏览器显示。

稳定期已观测 Chromium 进程累计 CPU 时间折合约 6.74 / 7.69 / 8.94 个 CPU 核心；它不是整机或服务器 CPU，也无法精确归因帧率下降。32 与 64 人阶段均触发低于 10 fps 的报告提醒。**这些结果证明本机多会话分流与解码进展，不证明 64 人流畅，更不证明百人容量。** 采样码率随实际画面和共享者输出变化，不能用低复杂度画面的实测出站值推算高码率生产容量。

首轮优化前数据也保留，但运行条件并非受控 A/B 实验，不按两轮帧率差异宣称画布优化的百分比收益。

### 真实持续共享

2026-10-21 本地约 12:09–12:19，5 位观众加 1 位共享者真实运行，稳定采样 **600.10 秒**，共 61 个样本，1/1 通过。期间每次采样各观众处理帧数均前进，2 个服务器供流节点、3 个同伴接收者的拓扑保持稳定，没有新增同伴连接，也没有页面未捕获错误；同伴的服务器媒体接收字节始终为零。

- 各观众平均解码帧率的最小值：23.36 fps。
- 稳定期服务器丢帧计数增量 0，拥堵上报增量 0。
- 平均服务器入站 / 出站：0.750 / 1.538 Mbps，仅代表本轮低复杂度合成画面。
- 观测到的页面 JS 堆合计约 50.08 MB → 25.34 MB；没有因此认定“无泄漏”，也没有测量服务器内存或整机 RSS。

这不是 64 位观众连续 10 分钟，更不是两小时真实播放。两小时逻辑时钟测试独立存在，不计入真实播放时长；物理断网、休眠与实际跨楼网络仍未验收。

## 如何复跑

前提：项目原有依赖、Playwright Chromium、Go 与受支持 Node.js 已就绪，且先按仓库约定阅读构建/发布手册。这些命令只启动本机虚拟站点，不用于公司压测。

在 `web` 目录的 PowerShell 中：

```powershell
npm run build
npm run test:relay

$env:RELAY_CAPACITY_VIEWERS = '16,32,64'
$env:RELAY_CAPACITY_SECONDS = '30'
npm run test:relay:capacity

$env:RELAY_SOAK_SECONDS = '600'
npm run test:relay:soak
```

- 容量人数只接受不重复的 16、32、64；稳定期允许 10–300 秒，默认 30 秒。
- 持续共享允许 60–7200 秒，默认 600 秒。`7200` 需要真实等待两小时，不会加速时间。
- 不要同时跑其他浏览器测试来污染容量/CPU 采样；也不要在接近内存极限时强行继续。
- 容量 JSON：`web/test-results/relay-capacity/results.json`，附件名 `capacity-report`。
- 持续共享 JSON：`web/test-results/relay-soak/results.json`，附件名 `endurance-report`。
- 本轮最终容量及持续共享 JSON 另存于被忽略的 `artifacts/relay-validation-20261021/capacity-results.json` 和 `soak-results.json`，以免下一次运行覆盖本轮依据。
- Playwright JSON 内的无文件路径附件使用 base64 `body`。结果目录被 Git 忽略，复跑同一入口前需自行保留要对比的历史结果。本轮首轮优化前采样另存于被忽略的 `artifacts/relay-capacity-20261021-before-render-change/results.json`。

## 仍然不能承诺的事

64 个会话集中在同一台机器，共享处理器、显卡和内存；动态合成画面复杂度低，不等于 64 台真实电脑、6 Mbps 高复杂度屏幕、跨楼网络或百人会议。真实使用需分开验证站点可达、授权、同伴路径、服务器回退预算及可接受的画质/延迟。

公司网络、外部访客接入、真实多设备容量、系统休眠冻结和服务器 CPU/RSS 尚未验收。此前的 Windows POSIX 文件权限测试及被忽略旧临时程序导致的全目录测试问题没有被绕过或宣称解决；Linux 全量/race/安全/容器发布闸门仍需补齐。详见 `BROWSER_RELAY_RESILIENCE_UAT.md`。
