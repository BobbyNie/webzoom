## 持续质量：失败，未降低门槛

沿用每位观众约 60 秒窗口、最低 15 fps 的原质量保护线；窗口由离散采样组成，并非精确每 60 秒。共 27 个有效窗口，10 个失败；最低观众窗口帧率 `0.9491 fps`，这 10 个窗口六位观众全部低于保护线。测试最终退出码 1，未重试后宣称通过。

全程平均六观众约 `16.77 / 16.78 / 16.78 / 16.74 / 16.79 / 16.76 fps`。这些均值虽高于 15，却掩盖后半段长时间约 1 fps，不能用全程均值冒充持续流畅。

| 连续共享时间 | 专用源动画更新频率 | 原生采集 | 排队 / 发送 | 观察 |
|---|---:|---:|---:|---|
| 1054.645 秒 | 164.62 Hz | 30.01 fps | 29.92 / 29.92 fps | 此时仍正常 |
| 1068.407 秒 | 159.57 Hz | 29.79 fps | 28.63 / 28.63 fps | 此段实际画质从 720p 转向 1080p；不据此断言因果 |
| 1084.437 秒 | 8.80 Hz | 1.31 fps | 1.25 / 1.25 fps | 已出现明显降速 |
| 1098.097 秒 | 7.69 Hz | 1.02 fps | 1.02 / 1.02 fps | 开始长时间约 1 fps |

134 个分段样本中，49 个采集帧率低于 5 fps。全部样本中源网页报告 `visible` 且 `focused=true`，但这些网页属性不能证明系统合成器、GPU、浏览器调度或原生采集器始终不受限制。末段真实截图也显示实际 `1198 × 1080 · 1 fps`，不是只看目标 `1080p · 30 fps`。

最大观察采集间隔约 1090.2 ms、发送间隔约 1099 ms，编码队列观察峰值仍为 1。本次新证据说明：降速不仅出现在接收端，源动画与原生采集供帧也同时下降，排队/发送跟随低供帧；**尚不能确定具体根因，更不能直接归因于 UDP 分流、网络、解码器、内存或系统省电**。

之前新增的播放停滞检测用于“数据继续到达但绘制停住”；本轮约 1 秒仍有新画面，未超过原 3 秒无绘制阈值。两者不是同一故障，不能把检测改动说成对持续低帧率的修复。

## 分流、恢复与清理：通过的具体部分

| 项目 | 证据 |
|---|---|
| 连续段拓扑 | 2 个服务器供流根节点 + 4 个同伴观众 |
| 4 位同伴服务器媒体接收字节 | 全部 0；各从同伴收到约 294 MB 压缩媒体 |
| 同伴真实传输 | host → host / UDP，开放且有实际字节的 DataChannel；不是 UDP 组播 |
| 3 次实际关闭根节点浏览器并补回观众 | 新画面确认约 3110 / 988 / 1040 ms |
| 实际刷新同伴页面 | 新画面确认约 3972 ms |
| 停止 → 原生重新捕获 | 3 轮完成；只证明能重新共享并产生新画面，不证明重启后持续恢复 30 fps |
| 最终停止共享 | 6 位观众角色均为 off，开放 WebRTC 连接均为 0 |
| 页面未捕获错误 | 0 |
| 测试退出后检查 | 曾记录的 79 个测试浏览器 PID 均未存活，本机 20443 测试端口无监听 |

恢复时间包含自动化轮询和新像素确认，不是精确媒体延迟。停止共享时会议 WSS 仍各有 1 条，这是会议仍在的控制连接；之后测试结束会议并关闭隔离浏览器。没有把开放 WebRTC 为零写成当时所有 socket 都为零。

## 资源与本机状态的有限证据

32 个有效资源样本均首次读取完整，无缺 PID 重试。测试浏览器进程私有内存总和：起点约 4001 MiB，峰值 5237 MiB，连续段结束约 2490 MiB，故障替换/重采集后的最终停止约 4141 MiB。资源采样时系统可用内存最低 998 MiB；之后曾回升到 5343 MiB，低帧率仍持续。这些计数不证明没有泄漏，也不足以确认或排除内存、GPU、系统调度的因果关系。

11:46:07 的一次只读本机状态查询显示：输入桌面可访问且名称为 Default、接通电源、电量 100%、系统电池节能标志为 0。它只是故障持续时单个时点的证据，不证明降速瞬间或此前没有锁屏、显示器变化、调度限制，也不能解释根因。未模拟鼠标键盘、点亮屏幕、调整电源方案或更改安全设置。

localhost 自签名证书探测出现预期的 TLS 握手警告，不代表生产证书链验证；测试器顶层的“达到最大失败数停止”对应最终质量断言失败，不是另一个页面异常。

## 当前结论与下一步

较早 15 分钟通过是独立历史基线，不能推翻本轮最终代码 30 分钟失败。本轮完成了用户要求的长测和完整留证，没有凭猜测修改产品性能代码。

下一步应先做能区分原因的本机对照：减少独立观众进程、分离源动画与原生轨道供帧/设置变化、观察目标画质切换和系统/浏览器状态，验证究竟哪一层先受限，再针对明确原因修复。不得先放宽 15 fps 保护线、跳过故障时段、强制禁用系统节能或把源动画降速直接解释为用户静态画面。

真实跨设备/跨楼栋/外部网络、64/100 台物理容量与完整 Linux CI/容器安全发布闸门仍未完成；继续保持“不正式就绪、不部署”的边界。
