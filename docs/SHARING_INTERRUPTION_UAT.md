# 共享无提示停止：本地修复与排查（2026-10-27）

## 已确认的代码问题

1. 共享者的 WebSocket 断开时，原有断线处理会停止本机 Publisher 与采集轨道。重连成功又会清除临时连接提示，但不会重新开始共享，因而用户可能只看到会议恢复连接，却不知道屏幕共享已停止。
2. 当前屏幕采集轨道触发 `ended` 时，原有回调停止本地及服务器共享，没有单独说明采集已经结束。
3. 服务端房间快照表明共享已停止、共享权已转交或共享 epoch 改变时，本机按原有安全边界停止 Publisher，没有独立的停止说明。

这些路径能解释“停止后没有提示”，但不能仅凭现象确定某次公司现场断开的触发原因。

## 本次修改

- 将意外停止说明与临时的连接/通用错误提示分开：保留停止类别、页面观察到的发生时间，以及 WebSocket 关闭代码（存在时）。不展示服务端任意关闭文本，不记录共享内容。
- 提示位于全屏元素内部，普通和原生全屏下均可见；重连成功或关闭通用错误不会清除它。重新成功共享或点击“知道了”才清除。
- 区分连接断开、浏览器采集结束、采集/编码异常及服务器共享状态变化。状态变化类别不冒充已知的具体服务器故障。
- 主动点击停止、离开，以及旧采集回调，不产生新的“意外中断”误报。
- 不改变自动重连与授权边界，不自动重新选择/传送屏幕；不通过延长登录有效期或修改公司网络配置来掩盖问题。

## 时间限制核查

本地代码中的会议最长有效期与登录会话上限为 8 小时；空会议的 30 分钟回收不是正在共享的固定时长限制。已经存在网页及服务端的登录续期逻辑，不能直接把此次现象归因于“登录半小时到期”。

仓库的 Route 模板中存在 `timeout` / `timeout-tunnel: 3600s`，但这不是公司当前实际 Route 配置证据，也不能仅凭数值断言“共享满一小时必断”。本轮未读取现场配置、未修改 Route、SSO、会议上限或服务端心跳。

## 用户补充与排查范围

2026-10-27，用户确认断开后共享者的按钮变回“共享屏幕”，不是仍显示“停止共享”但观众收不到画面。因此，本次现场现象应优先追查本机 Publisher 停止路径，而不是先归因于观众解码或同伴分流。

复查停止入口后，仍需区分：共享连接关闭（包括浏览器分流授权探测失败后关闭控制连接）、浏览器采集轨道结束、采集读取/编码错误，以及服务器停止共享/更新 epoch/转交权限。登录失效也会停止本机共享，但页面另有登录过期提示。按钮变化本身不能证明是哪一项，更不能证明已找到现场根因。

本地代码没有普通共享“满半小时自动停止”的规则。现有续期及功能测试通过，也不能排除现场代理、网络、浏览器或操作系统的实际中断。下一次使用本地候选版本时，持久提示可保留停止类别与发生时间；在获得该证据前，不以延长超时、自动重新共享或修改公司环境替代根因判断。
